## 3. 주요 의사결정

| ID | 결정 | 검토한 대안 | 이유 |
|---|---|---|---|
| D-01 | 카카오톡 "나에게 보내기"로 알림 발송 | 친구에게 보내기 | 친구 대상 자동 발송은 권한 심사가 필요하고 카카오 정책상 자동 발송을 지양함. 본인 알림은 심사 없이 사용 가능 |
| D-02 | 초대장·약속 조율 기능은 범위에서 제외 | 1차 제출 전 구현 | 1주 일정에서 핵심 기능(자연어 등록, 자동 발송)의 완성도를 우선 |
| D-03 | n8n Cloud, 10분 간격 실행 | 로컬 n8n, 5분 간격 | 로컬은 컴퓨터가 꺼지면 멈춤. 5분 간격은 체험판 실행 한도(1,000회)를 마감 전에 초과 |
| D-04 | n8n은 백엔드 내부 API만 호출 | n8n이 Firestore 직접 조회, 토큰 직접 갱신 | 토큰이 한 곳에서만 관리되어 보안과 중복 발송 방지가 단순해짐. 조건 미충족 시 다음 주기 재확인, 발송 후 `sent: true` 기록으로 합의 |
| D-05 | 프론트를 백엔드(FastAPI)에서 함께 제공, Render 하나로 배포 | 프론트 Vercel, 백엔드 Render 분리 | 도메인이 다르면 로그인 쿠키가 다른 사이트 쿠키로 취급되어 아이폰 사파리 등에서 차단될 수 있음 |
| D-06 | 날씨는 Open-Meteo 사용 | 기상청 단기예보 | 기상청은 격자 좌표 변환과 키 승인 시간이 필요. Open-Meteo는 키 없이 위경도로 조회 가능 |
| D-07 | 알림 종류를 trip과 reminder로 구분 | 약속 알림만 지원 | "매일 아침 7시 반에 영하면 패딩" 같은 반복 조건 알림 수요를 반영 |
| D-08 | RAG, Long-term Memory 미적용 | 기술 요소 수를 늘리기 위해 적용 | 실시간 데이터는 API 도구 호출이 더 정확하고, 대화형 서비스가 아니라 맥락 기억이 필요 없음 |

## 4. 문제 해결 기록

| 문제 | 원인 | 해결 |
|---|---|---|
| 프론트와 백엔드의 알림 등록 형식 불일치 | 프론트는 자연어 문장 하나를, 백엔드는 항목별 데이터를 기대 | 자연어 등록 API(`/api/alerts/natural`)를 추가해 AI가 문장을 항목으로 변환 |
| 사용자 토큰이 서버 메모리에만 저장 | 초기 구현에서 한 명분만 메모리에 저장, 서버 재시작 시 사라짐 | 사용자별 토큰을 Firestore에 저장하고 갱신 시 반영 |
| 로그인 후 화면이 넘어가지 않음 | 콜백이 JSON만 반환 | 세션 쿠키 설정 후 프론트로 리다이렉트, 로그인 확인 API 추가 |
| PR #8 머지 충돌 | 같은 파일(`frontend/js/main.js`)을 두 브랜치에서 수정 | 화면 동작 코드(develop 쪽)를 남기고 초기 테스트 코드 제거 |
| n8n 첫 실행 시 503 | Render 무료 서버가 15분 이상 요청이 없어 잠든 상태 | 재실행으로 해결. HTTP 노드 재시도 3회, 타임아웃 90초 설정. 10분 주기 호출로 서버가 깨어 있게 유지 |
| 같은 알림이 두 번 발송될 가능성 | n8n 재시도나 중복 호출 | 트랜잭션으로 알림을 선점(sending)한 뒤 발송, 이미 보낸 알림은 `already_sent` 응답 |
| 카카오맵 API 무료 쿼터 적용 문제 | 무료 쿼터가 기존 앱에 적용되어 있고 변경 문의에 대한 답변 지연 | 앱 분리 사용 방식 검토 및 적용 |
